Most sites don't fail because the code is bad. They fail because nobody watched what actually happens between the design file and the browser. At Mr B we build client sites for a living, and the same handful of mistakes show up again and again — on brochure sites, on e-commerce stores, on internal tools nobody outside the company will ever see. Here's what we've learned, told the way we'd tell a client over coffee.

  1. Design for the content you'll actually have

    Mockups get built with perfect placeholder text and a client's best product photo. Real content is messier — longer headlines, a logo that's slightly the wrong aspect ratio, a price that jumps to four digits during a sale. We test every layout with the ugliest realistic content we can think of, not the nicest.

  2. Performance is a design decision, not a cleanup task

    You can't compress your way out of a page that loads twelve fonts and four carousel libraries. The fastest optimization is deciding early what the page doesn't need. We set a size budget before we write a line of CSS, the same way you'd set a budget for a renovation.






  3. Test on the device someone will actually use

    Most traffic to most client sites is a mid-range phone on a mid-range connection, not a designer's monitor on office wifi. We keep a shelf of older, slower phones in the studio for exactly this reason. If it feels sluggish there, it ships slow to most visitors.

    • Check tap targets at actual thumb size, not mouse-cursor size
    • Throttle the network before calling something "fast enough"
    • Read every page with a screen reader at least once
  4. Ship it, then watch it

    Launch day isn't the finish line — it's when real data starts arriving. We keep an eye on load times and error rates for the first few weeks after any site goes live, because that's when the gap between "should work" and "does work" shows up.
